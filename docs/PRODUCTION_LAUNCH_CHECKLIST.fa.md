# چک‌لیست انتشار Production ویجنت

این فایل مرجع عملیاتی انتشار است. هیچ مقدار واقعی secret را داخل Git، خروجی CI،
اسکرین‌شات یا تیکت پشتیبانی قرار ندهید.

## ۱. دروازه پیش از انتشار

- روی سرور تازه، `bash deploy/setup-server.sh` را اجرا کنید و سپس کلیدهای سرویس‌های بیرونی را در `.env` وارد کنید.
- `npm run check:production-env` باید بدون خطا تمام شود. هشدارها را آگاهانه بررسی کنید؛ به‌خصوص بکاپ خارج از سرور و نرخ تبدیل مالی.
- متغیر `NODE_TLS_REJECT_UNAUTHORIZED=0` نباید در shell، PM2 یا `.env` وجود داشته باشد.
- پیش از هر انتشار، `npm ci`، `npx prisma generate`، TypeScript، تست‌ها، lint و build production باید سبز باشند.
- `npm audit --omit=dev` باید برای وابستگی‌های production بدون High/Critical باشد.

## ۲. زیرساخت و شبکه

- فقط پورت‌های لازم عمومی باشند: SSH مدیریت‌شده، HTTP برای redirect و HTTPS. PostgreSQL، Redis، MinIO و پنل‌های داخلی فقط روی loopback/private network بمانند.
- TLS معتبر، تمدید خودکار گواهی و redirect دائمی HTTP به HTTPS را در Nginx فعال کنید.
- محتوای `deploy/nginx-proxy-security.conf` را در `location /` قرار دهید؛ در غیر این صورت به `TRUST_PROXY_HEADERS=1` اعتماد نکنید.
- محدودیت اندازه درخواست و timeout جداگانه برای upload و webhook در Nginx تعریف کنید.
- DNS، رکوردهای ایمیل دامنه و دامنه‌های callback سرویس‌های Meta/پرداخت دقیقاً با URLهای production یکسان باشند.

## ۳. داده، بکاپ و بازگشت

- `deploy/deploy.sh` پیش از migration یک `pg_dump` اجباری می‌گیرد. انتشار در صورت شکست dump باید متوقف بماند.
- برای dump ابتدا `DIRECT_URL` استفاده می‌شود و پارامترهای مخصوص Prisma مثل `schema` حذف می‌شوند؛ خالی‌بودن `BACKUP_S3_*` مانع بکاپ محلی یا deploy نیست و فقط کپی خارج از سرور را غیرفعال می‌کند.
- `BACKUP_S3_*` را به یک فضای شیء مستقل از سرور برنامه متصل کنید؛ MinIO همان سرور بکاپ بحران محسوب نمی‌شود.
- حداقل ماهانه یک restore واقعی روی staging انجام دهید و زمان بازگشت و صحت شمارش رکوردها را ثبت کنید.
- ظرفیت دیسک PostgreSQL، MinIO و پوشه بکاپ هشدار داشته باشد. چرخه نگهداری باید با سیاست حذف/نگهداری داده مشتری هماهنگ شود.
- migrationها forward-only فرض می‌شوند؛ برای انتشارهای پرریسک برنامه rollback کد و restore داده از قبل نوشته شود.

## ۴. Smoke test پس از انتشار

- `GET /api/health` از بیرون ۲۰۰ بدهد و جزئیات داخلی خطا را افشا نکند.
- ثبت‌نام/OTP، ورود، خروج، لغو نشست کاربر حذف‌شده و MFA ادمین با حساب‌های آزمایشی بررسی شوند.
- ساخت ایجنت از onboarding، ساخت با هوش مصنوعی، ویرایش تنظیمات، نسخه‌بندی و پاسخ آزمایشی در هر دو زبان اجرا شود.
- برای هر کانال فعال، یک پیام ورودی واقعی، پاسخ خروجی، handoff اپراتور و شکست عمدی webhook آزمایش شود.
- callback پرداخت موفق، مبلغ/ارز/مالکیت، idempotency و تمدید اشتراک با sandbox و سپس یک تراکنش کم‌مقدار واقعی کنترل شود.
- upload مجاز و غیرمجاز، محدودیت حجم/تعداد، حذف فایل موقت و دسترسی غیرمالک آزمایش شود.
- صفحه اصلی، login، onboarding، overview، conversations، agents، billing و admin روی موبایل و دسکتاپ بازبینی شوند.

## ۵. پایش و پاسخ به حادثه

- uptime بیرونی برای سایت و health، ثبت خطا برای web و worker، و هشدار 5xx/latency/queue lag/DB connections/disk فعال کنید.
- شکست webhookها، افزایش OTP، مصرف غیرعادی اعتبار AI، جهش upload و پرداخت ناموفق باید هشدار قابل اقدام داشته باشند.
- لاگ‌ها نباید token، متن کامل secret، OTP، cookie، header امضا یا اطلاعات پرداخت را ذخیره کنند.
- مالک incident، راه ارتباط اضطراری، روش قطع موقت کانال/مدل/پرداخت و متن اطلاع‌رسانی مشتری از قبل مشخص باشد.
- کلیدها دوره‌ای و بلافاصله پس از هر احتمال افشا rotate شوند؛ دسترسی سرور و پنل سرویس‌ها حداقل‌اختیار و دارای MFA باشد.

## ۶. کیفیت، سرعت و جذب مشتری

- Lighthouse موبایل را پس از deploy برای `/` و مسیرهای اصلی هر دو زبان، با cache سرد و گرم، اجرا کنید.
- هدف محصول را بر Core Web Vitals واقعی قرار دهید: LCP، INP و CLS صدک ۷۵؛ امتیاز آزمایشگاهی تنها معیار انتشار نیست.
- Search Console، sitemap/robots، canonical/hreflang، structured data و index شدن صفحات فارسی و انگلیسی کنترل شوند.
- رویدادهای قیف `landing -> signup -> onboarding_complete -> agent_created -> channel_connected -> first_value -> paid` ثبت شوند، بدون ذخیره داده حساس گفتگو.
- شرایط استفاده، حریم خصوصی، سیاست نگهداری/حذف داده، رضایت پیام تبلیغاتی و امکان لغو دریافت با مشاور حقوقی بازار هدف نهایی شوند.
- پیش از تبلیغ گسترده، یک rollout محدود با چند کسب‌وکار واقعی انجام دهید و نرخ فعال‌سازی، زمان رسیدن به اولین ارزش، خطای پاسخ ایجنت و نرخ handoff را اندازه بگیرید.

## ۷. فرمان انتشار

پس از سبز شدن موارد بالا:

```bash
bash deploy/deploy.sh
```

خروجی موفق باید شامل build، بکاپ، migration، reload سرویس‌های PM2 و health check نهایی باشد.
